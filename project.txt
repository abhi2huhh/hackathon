INNOLEARN PROJECT SUMMARY
==========================

1. PROJECT IDENTITY
-------------------
Project name: InnoLearn
Repository: https://github.com/abhi2huhh/hackathon
Project type: Full-stack learning and career development platform
Architecture style: React single-page application plus Flask REST API
Deployment target:
- Frontend: Vercel
- Backend: Render
- Primary relational data: PostgreSQL in production, SQLite for local development/tests
- Authentication records: MongoDB Atlas support has been added

InnoLearn combines learning resources, technical roadmaps, resume analysis, document summarization, and document question answering in one authenticated workspace.

The product is designed for students and technical professionals who want to:
- Explore learning roadmaps
- Track progress through roadmap steps
- Search and bookmark educational resources
- Analyze a resume against a job role
- Summarize text or uploaded documents
- Upload documents and ask questions about them
- Manage their account securely
- Provide administrators with tools to manage users, resources, roles, and roadmaps

2. HIGH-LEVEL ARCHITECTURE
--------------------------

The browser runs the React frontend. The frontend calls the Flask backend through JSON and multipart HTTP requests.

Request flow:

    User browser
        |
        | HTTPS requests to /api
        v
    React + Vite frontend on Vercel
        |
        | VITE_API_URL
        v
    Flask API + Gunicorn on Render
        |
        +--> PostgreSQL / SQLAlchemy for application data
        |
        +--> MongoDB Atlas for authentication records when MONGODB_URI is configured
        |
        +--> Optional LLM providers for generated answers and abstractive features
        |
        +--> Local or persistent upload storage depending on deployment design

The backend uses Flask's application factory pattern. The main factory is create_app() in backend/app/__init__.py. It initializes database access, JWT authentication, CORS, rate limiting, blueprints, error handlers, and security headers.

The frontend uses React Router to separate public pages from protected application pages. Authenticated requests include a JWT access token from localStorage.

3. WHY THIS TECH STACK WAS USED
--------------------------------

React
- Component-based UI development
- Good support for interactive dashboards, forms, protected routes, and reusable components
- Works well with Vite for fast local development and optimized production builds

TypeScript
- Adds static type checking to frontend code
- Reduces errors in API responses, forms, component props, and route data
- Makes the frontend easier to maintain as the application grows

Vite
- Fast development server
- Fast production build pipeline
- Reads VITE_* environment variables during the build
- Suitable for deploying the generated dist directory to Vercel

Tailwind CSS
- Utility-based styling system
- Helps keep visual styling consistent
- Allows responsive layouts without maintaining a large custom stylesheet

Motion
- Provides page transitions and interface animations
- Used to make the interface feel responsive without writing complex animation logic

React Three Fiber and Three.js
- Used for the 3D knowledge visualization component
- Allows 3D scenes to be expressed with React components
- Provides a more distinctive visual identity for the learning interface

Flask
- Lightweight Python web framework
- Good for REST APIs and modular blueprints
- Easy to organize authentication, resources, analysis, and AI services separately

SQLAlchemy and Flask-SQLAlchemy
- ORM for relational database access
- Maps Python classes to database tables
- Handles relationships, foreign keys, queries, and transactions
- Used by most of the current application data layer

PostgreSQL
- Production relational database
- Suitable for users, roadmaps, progress, documents, resources, bookmarks, summaries, and activity logs
- Supports relational integrity and indexes better than a temporary deployment filesystem

SQLite
- Local fallback when DATABASE_URL is not configured
- Used for local development and tests because it is simple and requires no database server
- Should not be used as the production database on Render because Render service storage is not a reliable permanent database

MongoDB Atlas and PyMongo
- MongoDB Atlas is a managed cloud document database
- PyMongo is the Python driver used by this backend
- MongoDB support was added for authentication records
- The app preserves the SQL numeric user ID so existing SQL foreign keys and JWT-protected routes continue to work

JWT
- Stateless access-token authentication
- The backend creates a token after login or registration
- The frontend stores the token in localStorage and sends it as a Bearer token
- Protected Flask routes use flask-jwt-extended

Gunicorn
- Production WSGI server for Flask
- Render starts the backend with Gunicorn rather than Flask's development server

Pytest
- Backend test framework
- The existing suite validates authentication and the main modules

6. AUTHENTICATION FLOW
----------------------

Registration:
1. Frontend sends name, email, and password to POST /api/auth/register.
2. Backend validates required fields, email format, and password rules.
3. A SQLAlchemy User identity row is created.
4. If MONGODB_URI is configured, a MongoDB authentication document is created in the users collection.
5. The password is stored as a Werkzeug password hash, never as plain text.
6. The backend creates a JWT containing the numeric SQL user ID and role.
7. The frontend stores the access token and authenticated user data.

Login:
1. Frontend sends email and password to POST /api/auth/login.
2. Backend finds the corresponding SQL user identity.
3. If MongoDB is enabled, the password is checked against the MongoDB auth record.
4. If MongoDB is not configured, local/test mode falls back to the SQL password hash.
5. A JWT is issued with the existing numeric SQL user ID.
6. The frontend sends the token on later requests using:

    Authorization: Bearer <token>

Current-user request:
- GET /api/auth/me requires a valid JWT.
- The numeric identity is used to load the SQL user row.

Why the JWT identity remains numeric:
- Existing application tables use SQL foreign keys pointing to users.id.
- Existing routes convert the JWT identity into an integer.
- Replacing it with MongoDB ObjectId would require changing many routes and all user relationships.

Admin behavior:
- The JWT includes a role claim.
- Admin endpoints require the ADMIN role.
- Admin role changes update the SQL user and synchronize the Mongo auth record.

7. DATABASE DESIGN
------------------

PostgreSQL/SQLAlchemy remains the main application database.

The User table contains:
- id
- name
- email
- password_hash
- role
- created_at
- updated_at

Other relational records reference user IDs:
- resumes
- documents
- summaries
- bookmarks
- user progress
- activity logs

MongoDB authentication documents contain fields such as:
- sql_user_id
- name
- email
- password_hash
- role
- created_at
- updated_at

A unique MongoDB index is created on email.

This is currently a hybrid design, not a complete MongoDB-only migration. PostgreSQL is still required by the rest of the application.

9. APPLICATION FEATURES
-----------------------

Learning roadmaps:
- Roadmaps are divided into ordered steps.
- Users can mark steps complete.
- Progress is stored by user and roadmap step.
- The dashboard aggregates roadmap and progress information.

Resource library:
- Resources have categories, subjects, difficulty, type, URLs, tags, and descriptions.
- Users can filter and search resources.
- Users can bookmark resources.
- Administrators can create, update, and delete resources.

ATS-style resume analysis:
- Accepts supported resume files such as PDF and DOCX.
- Compares resume content with a selected job role.
- Produces an estimated compatibility score.
- Uses skill, keyword, semantic, experience, and education weights.
- This is an educational estimate, not an official employer ATS result.

Summarization:
- Supports text summarization.
- Supports uploaded document summarization.
- Extractive summarization works without an external LLM.
- Optional abstractive summarization can use configured providers.

RAG document question answering:
- Users upload PDF, DOCX, or TXT documents.
- Text is extracted and divided into document chunks.
- Retrieval finds relevant chunks for a question.
- Sentence Transformers embeddings are preferred when installed.
- TF-IDF cosine retrieval is the portable fallback.
- An optional LLM can generate an answer using the retrieved passages.
- Retrieval can still work when LLM keys are missing.

Admin management:
- View statistics.
- View users.
- Change user roles.
- Manage job roles.
- Manage learning resources.
- Manage roadmaps.

10. AI AND NLP DESIGN
---------------------

The application intentionally supports graceful fallbacks.

Embeddings:
- Preferred: Sentence Transformers models when the optional ML dependencies are installed.
- Fallback: TF-IDF and cosine similarity.

Language models:
- Together-compatible OpenAI API configuration is supported.
- Hugging Face keys can be configured.
- OpenAI-compatible keys and base URLs can be configured.
- LLM features are optional; the basic application runs without them.

This design keeps local development lighter and prevents the RAG and summarization modules from becoming unusable when an external provider is unavailable.

    MONGODB_DATABASE=innolearn

    ADMIN_EMAIL=admin@example.com
    ADMIN_PASSWORD=<strong admin password>

Optional AI variables:

    LLM_PROVIDER=together
    TOGETHER_API_KEY=<provider key>
    OPENAI_API_KEY=<provider key>
    OPENAI_BASE_URL=https://api.together.xyz/v1

Frontend Vercel variable:

    VITE_API_URL=https://hackathon-nbr0.onrender.com/api

Security rules:
- Never commit .env files.
- Never put DATABASE_URL, MONGODB_URI, secret keys, or provider keys in frontend variables.
- Only VITE_* variables are intended for frontend exposure.
- Rotate credentials if they are pasted into chat, screenshots, logs, or public repositories.
- Use long random values for SECRET_KEY and JWT_SECRET_KEY.

- Render starts Gunicorn and checks /api/health.
- The health route performs SELECT 1 through SQLAlchemy.

- psycopg2-binary is included in requirements.txt for PostgreSQL URLs.
- A healthy response looks like:

    {"data":{"database":true,"status":"ok"},"message":"","success":true}

15. DEPLOYMENT PROBLEMS THAT WERE FIXED
---------------------------------------

Problem: Render could not import psycopg2.
Cause: The PostgreSQL driver was missing from backend/requirements.txt.
Fix: Added psycopg2-binary.

Problem: Render searched for backend files in the repository root.
Cause: The service root directory was empty in a monorepo.
Fix: Set Render root directory to backend.

Problem: Render health checks returned 503.
Cause: The health route checks the SQLAlchemy database and DATABASE_URL was not configured or unavailable.
Fix: Configure a valid PostgreSQL DATABASE_URL and redeploy.

Problem: Frontend displayed a generic server error.
Possible causes:
- VITE_API_URL was missing or pointed to an old backend.
- The Vercel frontend was not redeployed after changing VITE_API_URL.
- The backend API returned a validation, authentication, or database error.
Fix: Set VITE_API_URL to the Render backend /api URL, redeploy Vercel, clear old localStorage tokens, and inspect the browser Network tab.

16. SECURITY MODEL
-------------------

Passwords:
- Passwords must never be stored as plain text.
- Werkzeug password hashing is used.
- MongoDB authentication documents store password hashes.

JWT:
- JWT_SECRET_KEY signs access tokens.
- Tokens are sent using the Authorization Bearer header.
- The frontend removes the token when a protected request receives HTTP 401.

CORS:
- Backend CORS is restricted to configured origins.
- Production should list the exact Vercel frontend origin.

Rate limiting:
- Flask-Limiter applies limits to reduce abuse, especially on login and registration routes.

Security headers:
- X-Content-Type-Options: nosniff
- X-Frame-Options: DENY
- Referrer-Policy: strict-origin-when-cross-origin

File validation:
- Upload size is limited.
- File extensions and MIME types are checked.
- Supported file types include PDF, DOCX, and TXT depending on the feature.

20. FINAL PROJECT DESCRIPTION
------------------------------

InnoLearn is a full-stack learning and technical career platform. The React frontend provides a responsive and interactive workspace for learning roadmaps, resources, resume analysis, summarization, and document question answering. The Flask backend exposes modular REST APIs and separates routing, models, validation, business services, authentication, and error handling. PostgreSQL provides the relational system of record for the current application, while MongoDB Atlas stores authentication records through a compatibility bridge. JWTs protect the API, and Vercel plus Render provide the intended frontend and backend hosting model.

The most important deployment fact is that MongoDB Atlas is currently part of the authentication design, but PostgreSQL is still required by the rest of the application. The application can only be deployed reliably when both database responsibilities are configured correctly, or after a complete migration of every remaining relational feature to MongoDB.
